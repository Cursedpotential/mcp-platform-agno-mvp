## 1. Data model — matter / document / fact

### Two `0001` migrations — NOT a dual-backend fork, and confirmed by the repo's own gap tracker as dead-ish

- `sql/0001_legal_os_bootstrap.sql` (115 lines) is the **full PostgreSQL schema**: 5 schemas
  (`legal_core`, `legal_research`, `legal_work_product`, `legal_release`, `legal_audit`),
  ~10 tables, a `legal_os_app` role with **no password** (line 14-16, `CREATE ROLE legal_os_app
  LOGIN` — no `PASSWORD` clause). Header says "Do not apply to production until an owner Type 1
  review" (line 4-5).
- `sql/0001_legal_os_sqlite.sql` (18 lines) is **not** a parallel port of that schema — it creates
  exactly **one table**, `legal_core_app_settings` (theme/timezone/confidential_mode/case_phase).
  Header: "Local SQLite stand-in for legal_core.app_settings. Live PostgreSQL apply of
  0001_legal_os_bootstrap.sql stays Type 1 HOLD" (lines 2-3).
- The **actual runtime SQLite schema** (24 tables) is generated by SQLAlchemy `Base.metadata.create_all()`
  from `api/legal_workspace/db/models.py` (438 lines), not from either SQL file. Table names are
  flattened (`legal_core_matter_ref` instead of `legal_core.matter_ref`) and the columns have
  **drifted from the Postgres SQL** — e.g. `LegalCoreMatterRef` (models.py:104-119) has
  `issue_tree`, `factor_matrix`, `last_agno_verify` JSON columns that do not exist in
  `0001_legal_os_bootstrap.sql`'s `legal_core.matter_ref` (bootstrap lines 34-40).
- `docs/URGENT-TODO.md` item **B2** (line 27) already documents this exact divergence and states
  the PostgreSQL bootstrap has **never been applied to the live cluster** — no `legal_os_app` role,
  no `legal%` schemas exist there (item **B3**, line 28). `db/store.py:69` calls `create_all()` and
  `engine.py:27` forces the SQLite branch whenever `store_dir` is non-null, so **even setting
  `DATABASE_URL` to Postgres would not currently create the Postgres tables** — this is a real,
  self-acknowledged defect, not paranoia on my part.

**Verdict**: neither `0001` file is "the" schema. Postgres bootstrap is aspirational/unapplied;
SQLite bootstrap is a 1-table stub; the SQLAlchemy ORM is the only schema that is actually live,
and it has drifted from both SQL files. This is real technical debt (schema-as-documentation vs.
schema-as-code have diverged), not a deliberate dual-backend design.

### Matter / document / fact model (from `db/models.py`, all 24 ORM tables)

- **Matter**: `LegalCoreMatterRef` (models.py:104) + `LegalCoreCourtCaseRef` (122). One matter is
  effectively hardcoded — see §5.
- **No `document` table and no `fact` table exist anywhere in this schema.** The closest things:
  - `LegalCoreSourcePackage` (138) — stores an entire imported `LegalSourcePackage` as one JSONB
    blob (`payload`), keyed by `package_id`. This is the sole "document/evidence" landing table,
    and it is opaque JSON, not normalized rows.
  - `LegalCoreExhibitAnnotation` (218) — owner metadata (Bates number, foundation, custody note,
    relevance, readiness) keyed to an `item_id`/`assertion_id` that originates in Agno. **No
    evidence bytes, no fact text** — see §4.
  - `LegalResearchAuthority` (267) — legal citation/case-law rows (not "facts" in the evidentiary
    sense — these are legal authorities like case citations and statutes).
  - Everywhere a "fact" is referenced, it is via `assertion_id: uuid.UUID` /
    `cited_assertion_ids: list[uuid.UUID]` (e.g. models.py:351-352, 405) — a **foreign reference to
    an entity that lives entirely in the sibling Agno repo**. Legal-Workspace never stores what the
    assertion actually says.

## 2. Document handling — there is no upload pipeline; the "document viewer" never leaves the browser

- Grepped the entire `api/` package for `upload`, `UploadFile`, `multipart`, `s3`, `boto3`,
  `r2_client` — **zero matches**. There is no `POST` endpoint anywhere that accepts a file.
- The only route that brings document-shaped content into the app is
  `POST /v1/legal-source-packages:import` (`api/main.py:515-523`), which accepts a
  `LegalSourcePackage` **JSON body** (not `multipart/form-data`) — a bundle of pre-hashed,
  pre-reviewed items that Agno is assumed to have already produced. `WORKSPACE.import_package()`
  (`services/workspace.py:417-437`) writes that JSON payload into `LegalCoreSourcePackage.payload`
  verbatim. There is no PDF/DOCX parsing, no OCR, no text extraction anywhere in `api/`.
- The web "Document viewer" (`web/src/app/documents/page.tsx` → `web/src/components/PdfPane.tsx`)
  is a **client-side-only, ephemeral PDF viewer**:
  ```tsx
  // PdfPane.tsx:14-20
  const [url, setUrl] = useState<string | null>(null);
  ...
  onChange={(event) => {
    const file = event.target.files?.[0];
    setUrl(URL.createObjectURL(file));  // browser-local blob URL
  }}
  ```
  The file is read with `<input type="file">` and rendered via `URL.createObjectURL()` in an
  `<iframe>`. **It never calls `fetch()` and never reaches the backend.** The component's own
  comment says as much: "This is not from the evidence store. In-browser editing and conversion
  are not available yet." (PdfPane.tsx:24-25). Refresh the page and the file is gone; nothing is
  stored, parsed, or indexed.
- **Redaction is real code, but it operates only on owner-produced files already on local disk**,
  not on anything uploaded through the UI: `services/redaction.py` uses `pikepdf` to find/replace
  literal byte tokens inside a PDF's decompressed content stream (`redact_content_stream()`,
  lines 59-91). It's a real, working technique for simple owner-typed PDFs, but a raw
  find-and-replace of raw bytes in the content stream will silently miss text broken across
  multiple `Tj`/`TJ` show-text operators (common with kerning-adjusted or wrapped text) or text
  drawn as an image — the function has no verification step for that failure mode beyond
  re-scanning for the literal token string (lines 82-83).

**Bottom line**: "Can a user upload a document?" — **No**, in the sense of a persisted upload. A
user can open a local PDF for on-screen viewing only, and can import a pre-packaged JSON bundle
that Agno produced. There is no ingestion pipeline this app owns.

## 3. Search — one outbound proxy to CourtListener; zero internal search

- `api/legal_workspace/services/sources.py` + `domain/sources.py` implement a generic,
  config-driven **outbound HTTP client** that GETs a external case-law search API and maps the
  JSON response into a `CaseHit` identity record (id/name/citation/court/date/url — no opinion
  text). The only configured source is CourtListener (`courtlistener_default_config()`,
  `domain/sources.py:93-124`), confirming the gap sheet's claim that research is hardcoded to one
  source (§2.3 "No configurable/pluggable research sources" — though the `SourceConfig` model
  *is* pluggable in shape, just never instantiated with a second source in code).
- The web UI wires this through `SourceSearch.tsx` → `GET /v1/sources/courtlistener/search?q=...`
  (component grep: `SourceSearch.tsx:25-26`), rendered on `web/src/app/case-search/page.tsx`.
- **There is no full-text search, no `LIKE`/`ILIKE` query, no vector/embedding search anywhere in
  the codebase.** Grep of `api/legal_workspace/db/store.py` (1066 lines, the entire repository
  layer) for `WHERE`, `.filter(`, `def .*search` returned **zero matches** — every read in that
  file is a full-table `SELECT` into a Pydantic list, filtered (if at all) in Python after the
  fact. There is no search over the user's own imported source packages, drafts, exhibits, or
  strategy notes — only over the outside world (CourtListener).
- `pgvector` and BM25 hybrid search are listed as dependencies/features the gap sheet says are
  **missing** (`GAP_SHEET_AND_REMEDIATION_PLAN.md` §2.3, §5 Category 4) — confirmed: `pgvector`
  does not appear in `pyproject.toml` (not independently re-verified here beyond the doc's claim,
  but consistent with the absence of any vector code in `api/`).

## 4. Evidence bundling / fact management

- **No fact/assertion table locally** (see §1) — assertions are referenced by UUID only.
  `AGENTS.md` (lines 16-24) states the boundary explicitly: "Do not ingest, hash, normalize, or
  establish evidence here. Cite accepted facts through `LegalSourcePackage` + exact spans. Missing
  proof → `EvidenceInvestigationRequest` back to the Evidence Platform." This is a deliberate,
  documented architecture choice, not an oversight — Agno is the fact/evidence system of record.
- **Citation model**: `LegalWorkProductDraftSection.citations` (models.py:327) and
  `LegalWorkProductWorkProductVersion.cited_assertion_ids` / `cited_authority_ids`
  (models.py:351-352) — a draft section carries a list of citation objects, each presumably
  pointing at an `assertion_id` + `span_locator` from an imported package, gated through
  `services/citation_gate.py` (`validate_factual_citations()`, called at
  `workspace.py:445` in `attach_factor_citation()`). This is a real, structurally-enforced
  gate: `attach_factor_citation` raises `ValueError` (workspace.py:447) if the citation doesn't
  validate against the currently-imported package.
- **Exhibit builder**: `domain/exhibits.py` — `ExhibitCandidate`/`ExhibitAnnotation` model owner
  metadata (label, foundation, custody note, redaction note, relevance, readiness) laid over
  imported package items. Explicitly "no evidence bytes" (`bytes_present: bool = False` field,
  exhibits.py:63) and "no seeded Bates numbers" (AGENTS.md:64). Bates numbering itself is real,
  working code: `bates_prefix()` and `next_bates_number()` (exhibits.py:69-87) deterministically
  slugify the matter name and find the next unused sequence number per prefix — but per the gap
  sheet (§2.5, §5 Category 5) it is "not fully wired to exhibit flow" end-to-end.
- **No "bundle"/production-export in the discovery sense** — the closest analog is
  `LegalWorkProductReleaseManifest` (models.py:396-409), a deterministic manifest of which draft
  sections + citations + omitted-private items constitute one release candidate, with
  `state: "release_candidate"` and `filed: bool` fields. `AGENTS.md:36` is explicit that release
  candidates "are deterministic manifests, not filings" and strategy/red-team/todo content is
  excluded from them by construction.
- **Chronology/timeline**: `LegalCoreDocketEvent` (models.py:160-174) is a manually-entered local
  calendar/historic-event table (`kind` in {hearing, deadline, foc, ...}), explicitly "Not Agno's
  authored factual timeline" (AGENTS.md:48). No auto-populated chronology from evidence exists.

**Verdict**: there is a real, structurally-enforced citation-gate and manifest system for
work product, but no local fact/assertion store — evidence bundling here means *annotating
references to Agno-owned facts*, not managing the facts themselves. This matches the documented
boundary, so it reads as intentional rather than an oversight, but it does mean the two repos'
schemas are **not duplicated** — Legal-Workspace genuinely does not have its own copy of the
evidence model (see §6).

## 5. Mock vs. real persistence — the ratio is better than the surface language suggests

- **Persistence is real, not mocked.** `docs/HANDOFF-2026-08-19-legal-workspace-persistence-and-build.md`
  (STATUS: PARTIAL, BUILD_STATUS: FAIL — that build failure was fixed in a later session per
  `GAP_SHEET…md` §0) documents the SQLite-as-source-of-truth refactor: every mutation writes to
  SQLite via `WorkspaceStore._write()` before the API returns; JSON files are only a debug mirror
  gated by `LEGAL_WORKSPACE_DEBUG_JSON` (config.py, `debug_json` field). 134-139 backend tests
  pass against this real store (`GAP_SHEET…md` line 11; `COMPACT-SUMMARY-2026-08-21.md` line 281).
- **The web pages fetch from the real API**, not from hardcoded arrays. Sampled 4 pages directly:
  `custody-factors/page.tsx` is an async RSC that calls `fetchFactors()` from
  `web/src/lib/api/client.ts` and renders whatever the API returns, with an explicit error path
  ("legal-api unreachable") if the fetch fails — this is wired to a real backend call, not mock
  UI data. `case-search/page.tsx` renders `<SourceSearch/>`, which does a real `fetch()` to
  `/v1/sources/courtlistener/search`. This pattern (thin Server Component → typed client fetch)
  appears to be the norm across the 31 routes (not exhaustively verified for all 31).
- **What actually is "mock"**: `scripts/seed_mock_workspace.py` (163 lines) POSTs synthetic rows
  through the **real HTTP API** into the **real SQLite store** — it is not a separate mock data
  layer, it is test data flowing through the production write path. Every field it writes is
  loudly prefixed `"MOCK"` (e.g. `"span_locator": "sms:mock:exchange-location"`,
  `"title": "MOCK — last FOC contact (test row, not clerk-confirmed)"`) so seeded rows are visibly
  distinguishable in the UI from real data — this satisfies the owner's global "test data must
  never become canonical" rule structurally (self-labeling) though nothing in the code currently
  purges these rows automatically; a human has to notice and clear them.
  **`docs/URGENT-TODO.md` item B4** independently confirms the dev SQLite DB currently holds
  seeded mock rows "that must never become canonical" and is also schema-stale (13 columns behind
  the ORM).
  **`AGENTS.md`** and `README.md` both state elsewhere that this Matter — the Genesee County
  custody case — **is** the one real matter this deployment is for; the seed script's MOCK rows
  are additive test rows layered on top of that one real matter's real (mostly empty) state, not
  a wholesale fake dataset.
- **What is genuinely fake/hardcoded (not mock-seed, but baked into code)**:
  - The single Matter itself is hardcoded: `services/workspace.py:145` sets
    `display_name="Genesee County custody matter"` and `:152` sets
    `court="7th Judicial Circuit, Genesee County, Michigan"` as defaults baked into the
    initial-state constructor, and `workspace.py:192` documents "Single-Matter session persisted
    under data/workspace/" — this is a single-tenant app by design, not a bug, but it means there
    is no multi-matter capability at all.
  - Agent model routing defaults to a placeholder string everywhere:
    `services/routing.py:35` — `model: str = "unevaluated-manual"` — and real invocation is
    hard-gated off by default: `config.py:33` — `invoke_models: bool = Field(default=False,
    alias="LEGAL_WORKSPACE_INVOKE_MODELS")`, checked at `services/workspace.py:626` and
    `api/privilege_routes.py:49`. So agent "runs" are recorded/routed but do not call a real
    model unless an operator explicitly flips that env var.

**Honest ratio**: persistence, API wiring, and most page-to-backend plumbing are real (not mock).
The content behind that plumbing is mostly empty/placeholder for a fresh install and gets
populated either by the owner's real single matter or by explicitly self-labeled MOCK rows from
the seed script. The deepest "fakeness" is not mock data but **stubbed behavior**: no real model
calls, no real document ingestion, no real search beyond one external API, single hardcoded
matter/court identity.

## 6. Relationship to the Agno platform (Agno-MCP-Platform)

- **Confirmed real, live, HTTP-only integration — no shared database, no shared code, no
  duplicated evidence model.**
- `api/legal_workspace/services/agno_client.py` (234 lines) is a small, deliberately narrow
  **read-only** REST client:
  - `probe_health()` → `GET {evidence_platform_base_url}/health`
  - `list_matters()` → `GET /v1/matters`, returns identity-only `MatterProjection(matter_id,
    display_name)` — explicitly "Evidence bytes, spans, and hashes stay on Agno" (line 33-34)
  - `verify_sha256()` / `verify_package_hashes()` → `POST /v1/verify/{sha256}` — hash-only custody
    verification, "Do not store evidence bytes" (line 181), fail-closed on any exception
    (lines 213-219 catch-all returns `ok=False`).
  - Every call is wrapped in try/except that fails closed rather than raising, and all calls carry
    a short 2s timeout / 0.4s connect timeout (lines 18-19).
- This client is actually used in production code paths, not just scaffolding:
  `workspace.py:685` calls `verify_package_hashes(hashes, client=agno_http)` inside
  `filing_readiness()` to compute a live custody-verification snapshot
  (`state.last_agno_verify`, the exact field that was found schema-drifted between the ORM and
  the SQL bootstrap in §1) — this is a genuine cross-service dependency exercised on a real
  user-facing endpoint (`GET /v1/filing-readiness`, main.py:551).
- `GET /v1/agno/status` (main.py:348) exposes `read_status()` (agno_client.py:165-177), a
  reachable/matters-visible health check, described in README.md:43 as "fail-closed, service
  names only."
- **The only outstanding gap here is auth wiring, not architecture**: `docs/URGENT-TODO.md`
  Pending Task #3 (also `COMPACT-SUMMARY-2026-08-21.md` §7 item 3) states Legal-Workspace still
  calls Agno directly at `http://evidence-platform:8000` instead of routing through the shared
  Context Forge gateway on port 4444 — a deployment/security-hardening gap, not a data-model or
  architecture gap.
- **No evidence model duplication was found.** Legal-Workspace's schema (§1, §4) contains zero
  tables that store raw evidence text, spans, or custody chains — every place that would need
  that data instead stores a UUID reference (`assertion_id`, `item_id`, `content_hash`) and, where
  verification is needed, makes a live call back to Agno rather than caching a local copy. This is
  the single most load-bearing architectural fact about the repo: **the boundary is enforced in
  code, not just in docs** — I found no bypass of it (no direct Agno DB connection string in
  config.py, no ORM model shaped like an evidence/assertion table).
