2. Universal workflow

Every source executes these stages. Each Activity has exactly one atomic responsibility, one side-effect boundary, one retry policy, and one receipt. A non-applicable stage writes an explicit not_applicable receipt; it never disappears or silently bypasses the contract.

Independent work may run in parallel—for example original-byte fingerprinting, container inventory, filesystem metadata capture, and embedded metadata extraction—but the workflow joins them before raw reconciliation. Use bounded child workflows or batches for large containers, heartbeats for long work, and Continue-As-New before history grows without bound. Never create one Temporal Activity per record.

Four hash computations; verification is separate

OutputHashesPurpose
H1Untouched original source bytesIdentity of the acquired binary/file.
Raw-record digest setExact raw spans, records, and attachmentsProves the lossless extraction pieces and supports raw-to-source coverage verification.
H2Each canonical normalized message/recordStable identity of each normalized member.
H3Exact ordered H2 membershipIntegrity of the sealed conversation or import generation.

H3 is not compared for equality with H1 because they hash different representations. Raw byte/span coverage is verified against H1; normalized H2/H3 membership is recomputed and verified against its sealed manifest.

  contract_version
  parser_id + parser_version
  source_version_ref
  format_id
  ordered raw records with exact locators
  source-native fields and encountered metadata
  attachment/member references
  rejected, malformed, unknown, and unparsed spans
  warnings and deterministic counts
}
Parser doesParser never does
Decode its declared formatHash or establish custody

Report attachments, failures, and unknown spansSchedule fallback, retries, or other tools

An adequate existing Python or other-language parser is reused. Go is required for the main orchestration runtime, not as a rewrite mandate for every parser.

4. Lossless raw and metadata contract

Preservation and interpretation are separate guarantees. The immutable original blob is the byte-for-byte authority. Raw extraction accounts for its logical records and retains exact bytes or byte-range/object references wherever a parser establishes them. Unknown or undecoded material remains retained with a reason; it is never dropped.

Metadata classExamplesRequired treatment
Filesystem/acquisitionPath, filename, size, birth/created/modified/accessed times, owner, permissionsKeep original values and identify the acquisition environment; these values may not be embedded in the file.
EmbeddedEXIF, XMP, IPTC, PDF/Office properties, email headers, GPS, device/software IDsKeep the complete native metadata object plus useful typed/indexed columns.
ContainerZIP members, folder hierarchy, internal timestamps, compression, archive headersCreate stable member/file locators and parent-child relationships.
Media/toolCodec, duration, dimensions, streams, thumbnails, extractor warnings/versionSeparate source metadata from tool-derived interpretation and record provenance.
Record-nativeUnknown JSON keys, flags, headers, reactions, edits, deletions, raw timestampsRetain every field in the source-format raw row even when normalization does not yet use it.

Each parser-declared source format has its own raw payload table. Those tables are physical subdivisions behind one PostgreSQL persistence Activity and one common base contract—not alternate workflows or destinations.

5. Enforced raw-to-normalized lineage

context.raw_record_identity
  ├── source_version_id
  ├── raw_generation_id
  ├── format_id + ordinal + exact locator
  └── context.raw_<format> (same id; native payload and metadata)

context.normalized_record_identity
  └── typed normalized table (same id)

context.normalization_lineage
  ├── normalized_record_id  FK → normalized identity
  ├── raw_record_id         FK → raw identity
  ├── source span / derivation role / field map
  └── normalizer id + version

The two identity spines contain identity and referential integrity, not a second copy of raw or normalized content. This preserves per-format raw tables while eliminating the current unenforceable raw_table TEXT + raw_id UUID pointer. The join supports one raw record producing multiple normalized records and one normalized record using multiple raw records.

Corrections create immutable amendment candidates and signal a reprocessing/reconciliation workflow. They never mutate the original raw generation.

7. Verified current drift

  • SBV currently performs upload retention, H1, parsing, H2/H3, conversion, SQLite persistence, audit, and in-memory job control inside the web service.
  • The existing Python Temporal workflow is inert, chat-specific, and uses the obsolete custody → parse → store → knowledge sequence.
  • The general ingest API bypasses Temporal through in-process/direct calls.
  • Full parser record arrays currently cross Temporal history.
  • No production writer was found for the existing six raw messaging tables; several ingest paths write normalized tables directly.
  • Current normalized-to-raw coordinates are nullable text/UUID pairs with no FK and are not populated by the normal store path.
  • Current raw coverage omits document, PDF, email, media, OCR, archive, and other source families; JSONB alone is not byte-lossless.

10. Non-negotiable acceptance gates

  1. Every entrypoint—agent, API, CLI, SBV, watcher, and bulk action—starts the same Go workflow.
  2. Every Activity has one atomic responsibility; no parse-and-store, normalize-and-persist, hash-and-commit, or seal-and-publish combination exists.
  3. Every adapter returns the same versioned raw envelope and cannot write canonical state.
  4. Every source has retained original bytes, complete metadata manifests, raw records, failures, and accounting receipts.
  5. Every committed normalized record has database-enforced raw lineage.
  6. Temporal history contains compact references only; restart and duplicate-trigger tests remain idempotent.
  7. SBV may be stopped while an agent starts, observes, and completes an import through the API.
  8. No source family has a shortcut, alternate database, reduced workflow, or silent skipped stage.
  9. Production completion requires commit, Coolify deployment, and live source-family verification.
