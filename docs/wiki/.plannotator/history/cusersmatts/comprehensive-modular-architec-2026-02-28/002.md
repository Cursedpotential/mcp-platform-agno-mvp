# Comprehensive Modular Architecture & GraphRAG-Centric Integration Plan (v4)

## 1. Executive Summary & Correction
You are absolutely correct: **MS GraphRAG is the orchestrator of the indexing and classification pipeline**, not just a retrieval tool at the end. Its primary power is taking text chunks, extracting entities/relationships, resolving them, running hierarchical community detection (Leiden algorithm), and summarizing those communities.

This revised plan places **MS GraphRAG at the center of the ingestion process**. 

However, MS GraphRAG's default behavior is to use expensive LLM calls for *everything* — especially entity extraction (which makes up 75%+ of its cost). 

**The Strategy:** We will use MS GraphRAG to orchestrate the pipeline, but we will **override its default entity extraction step**. Instead of calling an LLM, GraphRAG will call our local, modular tools (**Microsoft Recognizers-Text** for numbers/dates, and **GLiNER2** for names/events), drastically reducing costs while keeping GraphRAG's powerful clustering and community summarization intact.

## 2. Component Responsibility Matrix

### Phase A: Ingestion & Document AI (The "Readers")
*Goal: Convert raw files into normalized Markdown/JSON chunks.*
- **Docling (IBM) / DocStrange / Unstructured.io**: Local, primary parsers for standard PDFs, DOCX, HTML, and standard formats.
- **Amazon Textract**: Cloud-based fallback. *Specific route:* Screenshots of text messages and low-quality images.
- **LlamaParse (LlamaIndex)**: Cloud-based fallback. *Specific route:* Highly complex, malformed, or heavily nested PDFs.

### Phase B: The GraphRAG Indexing Pipeline (The Core Engine)
*Goal: MS GraphRAG manages the pipeline, but delegates specific tasks to our specialized local tools.*

#### 1. Entity Extraction Override (Local & Specialized)
- **Microsoft Recognizers-Text**: Local, Node.js. *Handles:* Dates, times, currency, percentages, dimensions, phone numbers. (As you noted, it does NOT do names, but it is perfect for all structured data).
- **GLiNER2 (Fastino)**: Local, Python. *Handles:* Names (Persons, Organizations), Locations, and Custom Custody Events (`custody_exchange`, `court_hearing`).
- **IBM Watson NLU**: Cloud, opt-in. *Handles:* Emotion analysis (anger, fear, sadness scores) and complex semantic roles.
- **Google Cloud NL + Maps API**: Cloud, opt-in. *Handles:* Structured address parsing and geocoding validation.

#### 2. Validation & Provenance Injection
- **Semantica (Hawksight-AI)**: Intercepts the entities *before* GraphRAG builds communities. It checks for conflicts against existing facts, requires Human-in-the-Loop (Rule #8) if a conflict exists, and attaches W3C PROV-O provenance.

#### 3. Community Detection & Summarization (GraphRAG Native)
- **MS GraphRAG (Leiden Algorithm)**: Groups the validated entities into hierarchical communities.
- **MS GraphRAG (Summarization)**: Uses the LLM to write summaries of these communities (e.g., "This cluster of communications shows a pattern of escalating tension regarding weekend custody").

### Phase C: The 5-Tier Database Storage (The "Vaults")
*Goal: Store the GraphRAG outputs in highly specialized engines for optimal retrieval.*
1. **DuckDB (Tier 1)**: First-touch storage. Holds the raw file blobs, file metadata, and the raw parsed Markdown chunks.
2. **LanceDB (Tier 2)**: Vector storage. Holds the embedded chunks and GraphRAG community summaries (via Ollama nomic-embed-text).
3. **Neo4j Dual-DB System (Tier 3 & 4)**:
   - **Neo4j DB #1 (Graphiti)**: Temporal memory graph. Tracks "episodes" (who communicated with whom, when, and where). Optimized for timeline queries.
   - **Neo4j DB #2 (Semantica)**: Absolute facts graph (`semantic_facts`). Stores the GraphRAG communities, validated entities, and W3C PROV-O provenance trails.
4. **MySQL (Tier 5)**: Standard relational state (users, sessions, UI configuration).

## 3. The End-to-End Workflow (Data Lifecycle)

### Step 1: Raw Ingest & DuckDB First-Touch
1. User uploads a file (e.g., `screenshot_of_texts.png` or `custody_order.pdf`).
2. **DuckDB** immediately records the file metadata and blob pointer.
3. The **Document Router** inspects the file:
   - `image/png` -> **Amazon Textract**.
   - `extreme complexity` -> **LlamaParse**.
   - `standard` -> **Docling / Unstructured**.
4. The parser returns clean Markdown, which is stored in **DuckDB**.

### Step 2: MS GraphRAG Indexing Initiated
1. **MS GraphRAG** takes the Markdown and splits it into text chunks.
2. GraphRAG reaches the "Entity Extraction" node. **We override the default LLM call.**
3. GraphRAG passes the chunk to our **Modular NER Router**:
   - **Recognizers-Text** pulls exact dates ("March 15th") and currency ("$500").
   - **GLiNER2** pulls the people ("John", "Jane") and events ("Custody drop-off").
   - **IBM Watson** (if enabled) tags the text with `{anger: 0.85}`.
4. The router formats these entities back into the standard GraphRAG format and returns them to the pipeline.

### Step 3: Semantica Validation & Conflict Check
1. Before GraphRAG builds relationships, the entities are passed to **Semantica**.
2. Semantica checks **Neo4j DB #2 (Semantic Facts)**. 
   - *Conflict Detected!* Document says exchange was at "School", but DB says "Police Station".
3. Semantica halts the pipeline and flags the UI. (Rule #8: Human resolves the conflict).
4. Once resolved, Semantica attaches W3C PROV-O metadata.

### Step 4: GraphRAG Community Detection
1. GraphRAG resumes. It runs the Leiden algorithm on the *validated* entities to cluster them.
2. GraphRAG uses the LLM to generate high-level summaries of these clusters.

### Step 5: Storage Distribution (LanceDB & Dual Neo4j)
1. The validated text chunks and GraphRAG summaries are embedded and sent to **LanceDB**.
2. Temporal data (The "Episode": John Doe exchanged custody on March 15th, anger=0.85) is written to **Neo4j DB #1 (Graphiti)**.
3. The absolute facts, communities, and provenance are written to **Neo4j DB #2 (Semantica)**.

### Step 6: Retrieval & Q&A
1. User queries: *"What is the history of custody exchanges involving high anger?"*
2. **Neo4j GraphRAG Python** dynamically generates a Cypher query.
3. It hits **Neo4j DB #1 (Graphiti)** to traverse the timeline of episodes.
4. It hits **Neo4j DB #2 (Semantica)** to pull the community summaries generated in Step 4.
5. It hits **LanceDB** to pull the semantic text of the actual text messages.
6. The LLM synthesizes the final answer, complete with exact citations.

## 4. Why This Workflow Wins
1. **Cost Efficiency**: We use MS GraphRAG for what it's best at (chunking, community clustering, and summarization) but replace its most expensive step (entity extraction) with local tools.
2. **Proper Tool Utilization**: Microsoft Recognizers-Text handles the complex regex math (dates/numbers/currency) flawlessly, leaving GLiNER2 to handle the nuanced NLP (names, events, abstract concepts).
3. **Data Integrity**: Semantica acts as a firewall *inside* the GraphRAG pipeline, ensuring no conflicting or unproven data ever makes it into the Neo4j databases without human approval.
4. **Modularity**: Every single tool in Phase A and Phase B is behind an interface. If LlamaParse becomes too expensive, we drop it. If DocStrange releases a better update, we swap it for Docling. The pipeline orchestration never breaks.
