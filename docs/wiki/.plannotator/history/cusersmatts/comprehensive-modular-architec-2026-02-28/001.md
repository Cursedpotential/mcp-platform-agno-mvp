# Comprehensive Modular Architecture & Integration Plan (v3)

## 1. Executive Summary
This document defines the complete, end-to-end data lifecycle for the MCP Tool Platform. It strictly adheres to the **5-Tier Database Architecture** while integrating a highly **modular, interchangeable pipeline** for Document AI and Entity Extraction. 

Every component is designed to be plug-and-play. If a module fails or a better technology emerges, it can be swapped without touching the core routing or database logic.

---

## 2. Component Responsibility Matrix

### Phase A: Ingestion & Document AI (The "Readers")
*Goal: Convert raw files into normalized Markdown/JSON chunks.*
- **Docling (IBM) / DocStrange / Unstructured.io**: Local, primary parsers for standard PDFs, DOCX, HTML, and standard formats.
- **Amazon Textract**: Cloud-based fallback. *Specific route:* Screenshots of text messages and low-quality images.
- **LlamaParse (LlamaIndex)**: Cloud-based fallback. *Specific route:* Highly complex, malformed, or heavily nested PDFs where local layout parsers fail.

### Phase B: NER & Enrichment (The "Extractors")
*Goal: Identify entities, relationships, emotions, and exact locations from the parsed text.*
- **GLiNER2 (Fastino)**: Local, primary. Zero-shot extraction of semantic entities (`person`, `event`, `communication`, `legal_proceeding`) and relations.
- **Recognizers-Text (Microsoft)**: Local, primary. Native Node.js extraction of structured data (`dates`, `times`, `currency`, `phone_numbers`).
- **IBM Watson NLU**: Cloud, opt-in. *Specific route:* Emotion analysis (anger, fear, sadness scores) and complex semantic roles.
- **Google Cloud NL + Google Maps API**: Cloud, opt-in. *Specific route:* When an entity is flagged as an `ADDRESS`, it routes to Google NL for structured breakdown, then to Google Maps API for real-world geospatial validation.

### Phase C: Validation & Provenance (The "Truth Filter")
*Goal: Ensure only verified, non-conflicting data enters the graphs.*
- **Semantica (Hawksight-AI)**: The gatekeeper. Handles W3C PROV-O provenance tracking, entity resolution, and conflict detection before writing to the databases.
- **HITL (Human-in-the-Loop) UI**: Triggered by Semantica (Rule #8) when data conflicts with existing absolute facts.

### Phase D: The 5-Tier Database Storage (The "Vaults")
*Goal: Store data in highly specialized engines for optimal retrieval.*
1. **DuckDB (Tier 1)**: First-touch storage. Holds the raw file blobs, file metadata, and the raw parsed Markdown chunks *before* they are chunked/embedded.
2. **LanceDB (Tier 2)**: Vector storage. Holds the embedded chunks (via Ollama nomic-embed-text or cloud).
3. **Neo4j Dual-DB System (Tier 3 & 4)**:
   - **Neo4j DB #1 (Graphiti)**: Temporal memory graph. Tracks "episodes" (who communicated with whom, when, and where). Optimized for timeline queries.
   - **Neo4j DB #2 (Semantica)**: Absolute facts graph (`semantic_facts`). Stores validated entities, verified relationships, and W3C PROV-O provenance trails.
4. **MySQL (Tier 5)**: Standard relational state (users, sessions, UI configuration).
5. *(Deprecated)* ChromaDB: Removed from architecture.

### Phase E: Abstraction & Retrieval (The "Thinkers")
*Goal: Provide LLMs with context.*
- **MS GraphRAG**: Batch processor. Generates global community summaries and hierarchical graph maps.
- **Neo4j GraphRAG Python**: Real-time retrieval package for dynamic cypher generation and local search.

## 3. The End-to-End Workflow (Data Lifecycle)

### Step 1: Raw Ingest & DuckDB First-Touch
1. User uploads a file (e.g., `screenshot_of_texts.png` or `custody_order.pdf`).
2. **DuckDB** immediately records the file metadata, hash, and stores a pointer to the raw blob.
3. The **Document Router** inspects the file:
   - If `type === image/png`, route to **Amazon Textract**.
   - If `complexity === extreme`, route to **LlamaParse**.
   - Else, route to **Docling / Unstructured**.
4. The parser returns clean Markdown.
5. **DuckDB** is updated with the parsed Markdown text linked to the original file ID.

### Step 2: Modular Entity Extraction
1. The Markdown text is passed to the **NER Router**.
2. **GLiNER2** runs locally (CPU) and extracts `{person: "John Doe", event: "Custody Exchange"}`.
3. **Recognizers-Text** runs locally (Node.js) and extracts `{date: "2024-03-15", time: "14:00"}`.
4. The router detects `custody_exchange` and flags the text for **IBM Watson NLU** to extract `{emotion: {anger: 0.85, fear: 0.2}}`.
5. The router detects a raw address string (`"123 Main St, Flint MI"`) and passes it to **Google NL + Maps API**, returning a validated, geocoded JSON object.
6. All entities and metadata are merged into an `ExtractedEntity[]` array.

### Step 3: Semantica Validation & Conflict Check
1. The `ExtractedEntity[]` array is sent to **Semantica**.
2. Semantica checks **Neo4j DB #2 (Semantic Facts)**. 
   - *Scenario A:* John Doe is already in the graph. The new event is appended.
   - *Scenario B:* The new document claims the exchange happened in "Detroit", but DB #2 says "Flint".
3. **Conflict Detected!** Semantica halts the automated pipeline and flags the UI. (Rule #8: Human resolves the conflict).
4. Once resolved, Semantica attaches W3C PROV-O metadata ("Fact X derived from Document Y via GLiNER2").

### Step 4: Storage Distribution (LanceDB & Dual Neo4j)
1. The validated text chunks are embedded (e.g., Ollama) and sent to **LanceDB** with metadata tags pointing to the Neo4j node IDs.
2. Temporal data (The "Episode": John Doe exchanged custody on March 15th, anger=0.85) is written to **Neo4j DB #1 (Graphiti)**.
3. The absolute facts (John Doe is the father, validated Address) and provenance are written to **Neo4j DB #2 (Semantica)**.

### Step 5: GraphRAG Abstraction
1. A user queries the system: *"What is the history of custody exchanges involving high anger?"*
2. **Neo4j GraphRAG** dynamically generates a Cypher query.
3. It hits **Neo4j DB #1 (Graphiti)** to traverse the timeline of episodes.
4. It hits **Neo4j DB #2 (Semantica)** to pull the exact, validated addresses and relationship facts.
5. It hits **LanceDB** to pull the semantic text of the actual text messages.
6. The LLM synthesizes the final answer, complete with exact citations and Map links.

## 4. Implementation Phasing

### Phase 1: Storage Foundation (Current/Next Step)
- Create `semantic_facts.ts` (Semantica interface).
- Wire `TrinityRouter.initializeAll()` in `server/core/index.ts`.
- Ensure DuckDB local initialization is stable.
- Configure dual connection strings for Neo4j (DB1 for Graphiti, DB2 for Semantica).

### Phase 2: The Document Router
- Create `server/mcp/ingest/router.ts`.
- Implement `DoclingAdapter`, `TextractAdapter`, and `UnstructuredAdapter` ensuring they all conform to a unified `DocumentParser` interface.
- Implement MIME-type and heuristic-based routing.

### Phase 3: The NER Router & Enrichment
- Create `server/mcp/ner/router.ts`.
- Implement the local pipeline (`GLiNER2Adapter`, `RecognizersTextAdapter`).
- Implement the cloud augmentation pipeline (`IBMWatsonAdapter`, `GoogleMapsAdapter`).
- Build the "Entity Merger" that deduplicates overlapping character spans from different modules.

### Phase 4: Semantica Integration
- Wire the output of Phase 3 directly into the Semantica Python bridge.
- Build the conflict-resolution UI hook for the frontend (Rule #8).

### Phase 5: Abstraction Integration
- Install MS GraphRAG for background batch-processing of communities.
- Expose the Neo4j GraphRAG Python retrieval endpoints to the Agno agent framework.
