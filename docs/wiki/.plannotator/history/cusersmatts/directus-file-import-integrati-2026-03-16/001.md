# Directus File Import Integration Plan

## Overview
Enable Directus web UI for file uploads that trigger the evidence processing pipeline (DuckDB → LanceDB → Neo4j), avoiding data duplication.

## Architecture Decision

**Proposed Flow:**
```
Directus Upload → PostgreSQL (metadata) → Webhook → MCP Tool → Evidence Processing
                                              ↓
                                    DuckDB (first drop, hashes + transform)
                                              ↓
                                    LanceDB (binary vault + embeddings)
                                              ↓
                                    Neo4j (knowledge graph + provenance)
```

**Key Integration Points:**
1. **Directus Storage Adapter** - Configure where files land
2. **Webhook on Upload** - Trigger MCP evidence processing
3. **PostgreSQL FK Tables** - Link Directus uploads to evidence records
4. **pg_duckdb Extension** - Query DuckDB from Directus

## Phase 1: Directus Configuration (30 min)

1. **Storage Setup**
   - Configure Directus storage (local/S3/compatible with LanceDB requirements)
   - Create `evidence_uploads` collection with metadata fields:
     - `original_filename`, `mime_type`, `file_size`, `uploaded_by`
     - `processing_status` (pending/processing/complete/failed)
     - `duckdb_hash`, `lancedb_id`, `neo4j_node_id`

2. **Permissions**
   - Setup role-based upload permissions
   - Configure field-level access for evidence metadata

## Phase 2: Evidence Processing Integration (45 min)

1. **PostgreSQL Schema Extensions**
   ```sql
   CREATE TABLE evidence_files (
     id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
     directus_file_id UUID REFERENCES directus_files(id),
     duckdb_hash TEXT NOT NULL,
     lancedb_vector_id TEXT,
     neo4j_node_id TEXT,
     processing_status TEXT DEFAULT 'pending',
     created_at TIMESTAMPTZ DEFAULT NOW(),
     processed_at TIMESTAMPTZ
   );
   ```
   Foreign key to `directus_files` - no file duplication, just metadata linkage.

2. **Webhook Configuration**
   - Create Directus Flow that triggers on `items.create` for uploaded files
   - Call MCP evidence processing endpoint (via Directus custom endpoint proxy)

## Phase 3: MCP Tool Pipeline (60 min)

1. **Create `/evidence/process` MCP Tool**
   - Input: `directus_file_id`, `original_path`, `metadata`
   - Output: `duckdb_hash`, `lancedb_id`, `neo4j_node_id`
   - Pipeline steps:
     - Hash calculation → DuckDB metadata insert
     - Binary storage → LanceDB with vector embedding
     - Entity extraction → Neo4j relationship graph

2. **Custom Directus Endpoint** (`/custom/evidence-process`)
   ```typescript
   // Express router for MCP tool proxying
   router.post('/evidence-process', async (req, res) => {
     const { directusFileId } = req.body;
     // Call MCP tool, return processing results
   });
   ```

## Phase 4: UI Customization (30 min)

1. **Evidence Upload Dashboard**
   - Custom Directus app extension for batch uploads
   - Processing status indicators
   - Evidence lineage visualization (link to Neo4j graph)

2. **Filter Panels**
   - Query DuckDB tables via pg_duckdb for fast metadata search
   - Vector similarity search through LanceDB integration

## Clarification Needed Before Implementation

**Question 1: File Storage Location**
- Where should Directus initially store uploaded files?
- Options: local filesystem, S3-compatible storage, or mount shared with LanceDB?

**Question 2: Processing Trigger**
- Should processing be synchronous (user sees progress) or asynchronous (webhook queues work)?
- Recommendation: Async with WebSocket status updates

**Question 3: DuckDB Role Confirmation**
- User said "DuckDB is first drop with transformation tools"
- Should transformed files stay in DuckDB, or is DuckDB purely metadata + results go to LanceDB?
- Current understanding: DuckDB = metadata + transformation results, LanceDB = binary + embeddings
