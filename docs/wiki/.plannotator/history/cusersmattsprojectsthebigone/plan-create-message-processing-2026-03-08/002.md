### 8. Input Validation - Detailed Brainstorming

#### 8.1 What Could Happen (Expected Behavior)
- User submits file without metadata → validation fails immediately
- Metadata has wrong `extraction_method` → not in enum, rejected
- Device identifier is empty or whitespace → rejected
- Extraction date is malformed → rejected
- Validation library (FEFE) throws unexpected error → generic failure

#### 8.2 What Could Go Wrong (Edge Cases)
- **Malformed JSON metadata**: If metadata passed as string instead of object, FEFE parsing fails with cryptic error
- **Unicode in device_id**: Right-to-left markers, emoji, combining characters causing minLength check to pass but later processing to fail
- **Date format edge cases**: ISO dates with timezone offsets, Unix timestamps as numbers, localized date strings
- **Case sensitivity**: "Manual" vs "manual" in extraction_method enum
- **Extra properties attack**: User includes malicious keys that bypass validation (though `allowExcessProperties: true` exists)
- **Missing vs empty strings**: `""` (empty string) vs `undefined` behavior differences
- **Race condition**: Metadata valid when validated but database schema changes before insertion

#### 8.3 Solutions to Fix

| Solution | Implementation | Files to Modify |
|----------|-----------------|------------------|
| Schema defaults | Add sensible defaults for optional fields, validate required fields first | coordinator.ts:104-114 |
| Better error messages | Return specific field name that failed validation | coordinator.ts:602-610 |
| Date normalization | Accept multiple date formats, normalize to ISO before validation | New utility function |
| Device ID sanitization | Strip whitespace, normalize Unicode, validate format | New validator utility |
| Metadata validation middleware | Add pre-validation in API layer before coordinator | API routes |
| Validation test suite | Unit tests for all valid/invalid combinations | tests/validation.test.ts |
| Enum case-insensitive matching | Accept "MANUAL", "Manual", etc. | coordinator.ts:108 |
| Structured error response | Return { field, expected, received, message } | coordinator.ts:605-609 |

#### 8.4 Implementation Approach

1. **Phase 1**: Create validation utility functions
   - `sanitizeDeviceId()` - removes whitespace, validates format
   - `normalizeDate()` - accepts multiple formats, returns ISO string
   - `validateExtractionMethod()` - case-insensitive enum check

2. **Phase 2**: Enhance error response structure
   - Define `ValidationError` interface
   - Map FEFE errors to user-friendly messages
   - Include validation context in response

3. **Phase 3**: Add client-side validation
   - UI validates before submission
   - Real-time feedback on required fields
   - Dropdown for extraction_method

### 9. Format Detection - Detailed Brainstorming

#### 9.1 What Could Happen (Expected Behavior)
- User uploads `.xml` → detected as SMS backup XML
- User uploads `.html` → detected as Facebook export
- User uploads `.json` → detected as ChatGPT export
- User uploads `.txt` → detected as WhatsApp export
- User uploads other extension → `unknown` → error response

#### 9.2 What Could Go Wrong (Edge Cases)
- **Double extensions**: `file.xml.txt`, `archive.zip.json` - only checks end
- **Case sensitivity**: `.XML` vs `.xml` vs `.Xml` behavior
- **Symlinks/links**: File path to symlink, target has different extension
- **Partial uploads**: File header matches but body is different/corrupt
- **Large files**: Magic byte read times out or OOM for 100+ MB files
- **Platform confusion**: Facebook export that contains WhatsApp-like patterns
- **Unicode filenames**: Non-ASCII characters in filename affecting extension detection
- **Archive files**: User uploads `.zip` containing message files - blocked
- **Ambiguous content**: `.json` that's actually a config file, not ChatGPT export
- **Text encoding**: Files with BOM, non-UTF8 encoding breaking detection
- **Multipart files**: Files with MIME-type headers but no clear extension

#### 9.3 Discovery: Facebook Parser Discrepancy

**Important Finding**: There are TWO Facebook parser implementations:
1. **Stub version**: `server/mcp/ingest/readers/FacebookHtmlReader.ts` - throws "not implemented" (used by coordinator)
2. **Working version**: `server/mcp/loaders/facebook-parser.ts` - fully implemented with streaming

The coordinator's `FacebookHtmlParser` class (lines 349-356) is a stub, but there's a complete parser in `loaders/` that could be adapted.

#### 9.4 Solutions to Fix

| Solution | Implementation | Files to Modify |
|----------|-----------------|------------------|
| Extension normalization | Use `.toLowerCase()` consistently, strip whitespace | coordinator.ts:210 |
| Double-extension handling | Parse all extensions (e.g., `.json.gz`), check each | coordinator.ts:209-263 |
| Archive detection | Detect `.zip`, `.tar`, `.gz`, prompt for extraction | New detector |
| Content-based detection | Read file headers beyond magic bytes, use heuristics | coordinator.ts:209-263 |
| Pluggable format detectors | Allow registration of custom format detectors | New detector registry |
| Multipart handling | Parse MIME boundaries, extract actual files | New parser utility |
| Encoding detection | Use `jschardet` or `iconv-lite` to detect encoding | New utility |
| Use working Facebook parser | Replace stub with `loaders/facebook-parser.ts` | coordinator.ts:349-356 |
| ChatGPT JSON parser | Implement for `loaders/` directory | New file: loaders/chatgpt-parser.ts |
| Expand format enum | Add PDF, EML, MSG, VCF support | coordinator.ts:49 |
| Graceful fallback | Return "partial_success" if some messages parse | coordinator.ts:677-739 |

#### 9.5 Implementation Approach

1. **Phase 1**: Enhance format detection robustness
   - Add `normalizeExtension()` function
   - Add `parseExtensionList()` for `.file.ext.zip` patterns
   - Add encoding detection
   - Improve magic byte detection (more file types)

2. **Phase 2**: Plug parser gap
   - Move `loaders/facebook-parser.ts` logic into coordinator's parser interface
   - Implement `ChatgptJsonParser` using existing patterns
   - Update parser registry to use new implementations

3. **Phase 3**: Add archive support
   - Detect `.zip`, `.tar.gz`, `.rar` files
   - Extract and process contained files
   - Add metadata for source archive
