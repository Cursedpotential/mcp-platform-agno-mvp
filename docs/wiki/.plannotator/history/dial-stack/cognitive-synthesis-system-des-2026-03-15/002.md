## Problem Statement

The user's cognitive process for forensic/narrative biographical writing involves 8 core domains, 10 frameworks, and 7 cognitive patterns. Goal: make it systematic, repeatable, tool-supported via skill/agent/prompt system **on top of existing dial-stack infrastructure**.

---

## Core Architectural Principle: Bidirectional & Tool-Agnostic

**The platform is fully bidirectional. All data can flow any direction.**

### Multiple Frontends
- **DIAL Chat** (port 3000) — Dev/admin interface
- **External agents** — Any AI agent can call tools directly
- **Custom frontends** — React + CopilotKit, future UIs
- **CMS** — Content management system integration
- **CLI/Script** — Direct Python API calls

### DIAL is Optional, Not Required
- Tools work **with or without DIAL**
- DIAL is an orchestration layer, not a gatekeeper
- Any tool can be called directly via Python API
- DIAL wraps tools for orchestration but isn't required for access

### Everything is an Atomic Tool
- Every capability is exposed as an independent, callable tool
- **Workflows are also tools** — composite tools that orchestrate atomic tools
- Workflows get called just like atomic tools
- No special handling needed — a workflow is just a tool that calls other tools

### Implementation Pattern
```python
# Atomic tool — works standalone
@mcp.tool()
def detect_hap(text: str) -> dict:
    """HAP scoring. Works standalone or via DIAL."""
    ...

# Workflow tool — composite of atomic tools
@mcp.tool()
def analyze_evidence(text: str) -> dict:
    """Full evidence analysis workflow. Also a tool."""
    cleaned = redact_pii(text)
    lang = detect_language(cleaned)
    hap = detect_hap(cleaned)
    behavioral = user_detection_system(cleaned)
    return {"cleaned": cleaned, "lang": lang, "hap": hap, "behavioral": behavioral}
```

### Data Flow (Bidirectional)
```
Any Frontend → Any Tool → Any Storage Tier
     ↑              ↓           ↓
     └──────────────┴───────────┘
         Data flows ANY direction
```

## IBM Data Prep Kit (DPK) — Pre-Processing Layer

**Package:** `data-prep-toolkit-transforms` v1.1.7 (PyPI)
**GitHub:** https://github.com/IBM/data-prep-kit (910 stars, Apache-2.0)
**Role:** Pre-processing layer that feeds cleaned data into user's custom detection system

### Key Insight
DPK uses the **same libraries** we were going to use (spaCy, Flair, Transformers, NLTK). IBM Granite models are well-suited for abuse/toxicity detection. DPK does NOT replace the user's custom detection system — it handles upstream data prep (PII redaction, language ID, doc quality, chunking) so the custom system gets clean input.

### Relevant Transforms

| Transform | Model/Library | Hardware | Use Case |
|-----------|--------------|----------|----------|
| **HAP** | `ibm-granite/granite-guardian-hap-38m` (38M params) | CPU, 6.16k tok/sec | Hate/Abuse/Profanity scoring (0-1 per sentence) |
| **HAP (large)** | `ibm-granite/granite-guardian-hap-125m` | CPU/cloud, 1.14k tok/sec | Higher accuracy HAP scoring |
| **PII Redactor** | Microsoft Presidio + Flair NER | CPU | Detect/redact PERSON, EMAIL, ORG, DATE, PHONE, CREDIT_CARD |
| **Lang ID** | fasttext | CPU | Language identification |
| **Doc Quality** | Custom scoring | CPU | Document quality scoring |
| **Doc Chunk** | Configurable | CPU | Document chunking for RAG |
| **Docling2Parquet** | Docling (already in stack) | CPU | PDF/DOCX → Parquet conversion |
| **Text Encoder** | Sentence transformers | CPU/GPU | Text embedding generation |
| **Readability** | Standard metrics | CPU | Readability scoring |
| **EDEDUP/FDEDUP** | mmh3/xxhash | CPU | Exact and fuzzy deduplication |

### Integration Pattern
```
Raw Evidence → DPK Pre-Processing → User's Custom Detection System → Dial-Stack Storage
                 │                        │
                 ├─ PII Redaction         ├─ Behavioral patterns
                 ├─ Language ID           ├─ DARVO detection
                 ├─ Doc Quality           ├─ Coercive control
                 ├─ HAP baseline scoring  ├─ MCL factor mapping
                 ├─ Doc Chunking          ├─ Narrative analysis
                 └─ Readability           └─ Custom scoring
```

### IMPORTANT: User's Custom Detection System
- User has their own detection system they worked hard on
- DPK does NOT replace it — DPK is upstream pre-processing only
- User's system handles: behavioral patterns, DARVO, coercive control, custom scoring
- DPK feeds clean, pre-processed data into user's system

## Implementation Plan

### Sprint 1: DPK + User's Detection System (Week 1-2)

**Goal:** DPK pre-processing feeding into user's custom detection system

1. **Install DPK transforms** in py-mcp-server:
   ```bash
   pip install data-prep-toolkit-transforms[language]
   ```

2. **Create `py-mcp-server/src/tools/dpk_tools.py`** wrapping DPK transforms:
   - `dpk_hap_score` — HAP scoring using IBM Granite 38M model (CPU)
   - `dpk_pii_redact` — PII redaction using Presidio + Flair (CPU)
   - `dpk_lang_id` — Language identification using fasttext (CPU)
   - `dpk_doc_quality` — Document quality scoring (CPU)
   - `dpk_doc_chunk` — Document chunking for RAG (CPU)
   - `dpk_readability` — Readability metrics (CPU)

3. **Connect to user's custom detection system** — DPK output feeds into user's system

4. **Create secondary Semantica database** for agent workspace

5. **Update DIAL config** — add `data-prep-tools` application

6. **Create skill documents** (Rule 5)

7. **Update TOOL_CATALOG.md**

### Sprint 2: Wire Existing Agents (Week 3-4)

1. **Add DIAL applications** for existing agents (forensic, custody-support, michigan-law)
2. **Extract behavioral analysis ontology** as training/seed material
3. **Test end-to-end** with existing evidence data

### Sprint 3: Enhancements (Week 5+)

1. **Fine-tune models on Colab Pro** using behavioral analysis ontology as training data
